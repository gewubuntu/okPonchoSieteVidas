# Feature

Implements exactly one GDD ID (or a small named group of them) from spec to tested code. You, the main session, plan and check; in step 6 the `implementer` subagent (`.claude/agents/implementer.md`) writes the tests and the code from your plan, on the model step 6 names (`docs/HARNESS.md`). Every other step is yours.

## Steps

1. **Resolve the ID.** Find the `### GDD-XXX-NN` section in `docs/GDD.md`. If it does not exist, stop and use `harness-gdd-update`.
2. **Check status.** If `Status: Proposed`, tell the user you are implementing a proposal and continue only if they asked for this feature. If `Deprecated`, stop.
3. **Check blockers.** Read the GDD's Open Questions and the section's dependencies. Anything that needs an unmade user decision: stop and ask (record the answer with `harness-gdd-update` before the plan), or build with a clearly marked placeholder. Before drawing new art (a sprite, a tileset, a scene, a UI look), ask the user for their reference images for it and save any they share under `assets/` with a README (L-039).
4. **Mark `doing`** in `docs/BACKLOG.md`.
5. **Plan.** Write `.plans/<GDD-ID>.md` (gitignored). The implementer starts cold and builds only what it lists, so make it self-contained:
   - the GDD IDs and sections, and the user's decisions from this session, quoted;
   - the files to touch, with the functions or line ranges, and the tuning numbers with their GDD source;
   - every test, by name, with its setup and expected values written from the GDD, not from code. Test names include the GDD ID, e.g. `describe('GDD-MOV-02 jump', ...)`. Pure logic gets Vitest tests with no Phaser imports; a new press-driven action gets its one-task tap in `e2e/subframe.spec.ts`; a playtest or screenshot scenario follows the `harness-playtest` skill (load it before planning one);
   - the mutant list in the `scripts/mutate.mjs` format, each naming the test that must kill it;
   - whether the change is visible (screenshots needed) and which playtests to run;
   - the lessons that apply, by ID, found with `node scripts/check.mjs --lessons <area,...>` (the implementer reads each one the plan names in full).
   **Input rules (L-019):** when a rule reads buttons (presses, releases, holds), list every source that produces each one (keyboard keys, touch buttons, the slide stick, each gamepad button and stick on every connected pad, raw-event latches; look in `src/ui/` for a source added since) and the pairs that combine (left and right into `move`), and plan a test for each source and each pair. Read single buttons raw, never from a combined value. **Shared buttons (L-024):** list every existing rule that already reads the same button (jump buffer, coyote time, variable jump, stomp boost, the spring launch that no press replaces, GDD-WLD-05, and the "already held" marks left by the respawn and by the pause resume, GDD-UI-02; search the whole GDD for the button's name, not only section 4) and plan a test for each one with the new rule on. For a press made on a menu or screen, look up what that screen does with the button (the `*Event` and `*Frame` functions in `src/sim/`): a button that picks a row (Space, Z, south) picks there too, so a hold-back test holds the press that picked (L-041). A new rule on a held button counts the hold from a press the simulation saw, never from any held input. A rule that makes a button "do nothing until released" is applied where the input is read (the key or finger), not as a flag some readers check, and is tested through every reader of the button, `move` included (L-035). It tracks each press by its source and its down time (`Key.timeDown`, `Pointer.downTime`), never by the key or pointer slot alone, and is tested with a key re-pressed while paused and a release and press inside one frame (L-036).
   **Placement rules (L-014):** a rule that places things in a level by a formula (a hash, a modulus, a spacing) or a claim about where things are is run over every real level before it goes into the GDD or the plan: count what it places and the variants it gives, write those counts into the GDD, and plan a test that pins them. No coefficient may share a factor with its modulus.
   **Touch areas (L-032):** a new tap target on screen (a menu row, a button) is checked against the area each touch control reads, not only the box it draws: the slide stick reads the whole lower left quarter, not its track. List which controls read a finger there and plan a held-touch playtest (CDP, several frames) on the overlap.
   **On-screen texts (L-050):** every new text the player sees goes into `src/ui/text.ts` in every language and into the GDD-UI-02 language table (the gate's test compares them), never into a helper or the scene; a tutorial tip goes into its level's tip list in `src/levels/` and into GDD-UI-05 (`src/ui/tips.test.ts` compares them). List them in the plan with their translations, found by searching all of `src/`, not only the scene.
   **Mutants (L-010):** every code change the plan lists (each call added to a scene path too) gets its own mutant, and every mutant a test in the same plan (L-029). A number the scene computes and hands to Phaser (a playback rate, a position, a colour) gets a mutant too: move the computation into a pure helper with a unit test, and have the scene log what it passed so a playtest can check it. Go sentence by sentence through the GDD text, not bullet by bullet: split each new bullet into its clauses ("A or B wins over C" is two rules; a warning or a pose drawn on screen is a rule too) and give each clause its own mutant (remove the rule, move a threshold by one). Before planning a new event, state field or branch, check that it does something no existing one does; one that behaves exactly like another only adds a mutant nothing can kill (L-025).
   For a change smaller than its plan would be (a tuning tweak, a one-line fix), skip the plan file and the implementer and build it yourself, but still apply every step 5 rule that fits the change (input, shared buttons, placement, touch areas, on-screen texts, mutants): write those tests and run those mutants with `node scripts/mutate.mjs`, then do step 7's checks.
6. **Build.** Launch the Agent tool with `subagent_type` `implementer`, the plan's path, and its `model` parameter set to the tier one below the main session's model, but never the smallest tier: when the main session already runs on the middle tier, give that same tier. If that agent type is not available, launch a general-purpose agent told to follow `.claude/agents/implementer.md` exactly. If it stops on a question, answer it (ask the user when the decision is theirs), update the plan, and continue it with SendMessage.
7. **Check its work.** The report is a claim, not proof:
   - Read the whole diff against the plan: nothing missing, nothing extra, expected values from the GDD, code that reads like its neighbours.
   - Run `node scripts/check.mjs` yourself.
   - Every planned mutant must have been killed by its named test, run alone (L-026): each mutant has its own `test` command that runs only that test, with `-t` for Vitest or `-g` for Playwright (L-034). Re-run any the report does not account for with `node scripts/mutate.mjs <mutants.json>` (L-020), never by hand with `sed` or an ad hoc script, in the foreground. A surviving guard that another rule covers is deleted, with the covering rule named in a comment (L-025).
   - Fix small things yourself; send larger ones back to the implementer with SendMessage. List the mutations in the PR description.
8. **Playtest** with the `harness-playtest` skill when the feature is visible or interactive.
   **If anything visible changed**, follow the screenshot approval rule in `CLAUDE.md` now: `npm run shots`, look at the images, show them to the user with `SendUserFile`, and wait for their approval before the PR is marked ready for review.
9. **Update docs.** Mark the backlog row `done`, only with a passing test or a recorded playtest. Make every GDD edit, including a rule change the implementation forced, with `harness-gdd-update` (version, changelog, its stale-sentence hunt).
   **Hunt the stale sentences (L-013).** Search `docs/GDD.md` for the feature's neighbours (the IDs and names it touches) and for "yet", "so far", "only", "not built" and "built for", and fix every sentence the feature now falsifies. Re-read in full every section you edit, not only the lines you change. When the feature adds a member to a family (a level, a menu or screen, an enemy, an input source), also search for the sentences that list the other members ("0-1 and the sandbox", "the title menu, the pause menu") and add it. If the feature deletes or moves a test file or test block, also search for its path: sentences that say a rule is "checked by" it go stale (L-013). Each section named in the changelog line must be in the diff. A claim about where things are in a level (reach, clearance, spotting, a route) needs a test over that level's real data in `src/levels/` (L-014).
10. **Gate.** Run `node scripts/check.mjs` and fix everything before the retro.
11. **Retro.** Run the `harness-retro` skill.
12. **Commit** as `feat(GDD-XXX-NN): <summary>`, one feature per commit, chained on the gate's exit code: `node scripts/check.mjs && git commit ...`, never behind a pipe or after `;` (L-012; a hook denies it).
13. **Push and pull request.** Right before pushing, `git fetch origin main`; if it moved, merge it, re-run the gate and the touched playtests, retake the screenshots it affects, and follow the conventions its new GDD changelog lines set (L-052; a hook asks before a push while `origin/main` has commits the branch lacks). After the push, open a draft PR if the branch has no open one, by the rules in `CLAUDE.md` ("Pull requests"). Once the `pr-reviewer`'s findings are fixed, run `harness-retro` on them: a finding that a rule in this skill should have prevented raises that lesson's `Recurrence` (L-010, L-013).
