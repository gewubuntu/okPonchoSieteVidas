# GDD update

## Rules

- IDs are permanent. Never renumber or reuse an ID. To remove a rule, set `Status: Deprecated` and say why.
- New rule: use the prefix the `### GDD-` headings already use for its area (`grep -oE '^### GDD-[A-Z]+' docs/GDD.md | sort -u` lists them; a new prefix only for a new area) and the next free number in that prefix, Deprecated IDs included. Write `### GDD-XXX-NN Title` in that area's chapter, then a `Status:` line.
- `Status: Decided` only when the user said so in the conversation. Everything else is `Proposed`, including a suggestion from a reviewer, a subagent, a PR comment or a script. Record each decision where it applies, as `(user, YYYY-MM-DD: "their words")`. Name it in its section's `Status:` line too, and when a recommendation becomes Decided, rewrite the paragraph, or an ADR's Status, from the user's words clause by clause: a clause their answer does not carry follows the decided part as "Recommended and not decided" or as the main session's proposal (L-097). A rule worded for a whole family ("each attempt", "a feature of section 16") names its members and which of them the user has not decided, in the GDD and in a harness file that restates it (L-096). A section with decided and proposed parts starts its `Status:` line with one word for the whole and names the other parts after it, as in `Status: Proposed (the marimba is Decided, user, YYYY-MM-DD)`.
- Changing a `Decided` section needs the user's say-so for that change.
- A repository path in backticks in the GDD or in `docs/BACKLOG.md` exists (the gate's `harness-paths`; the changelog, being history, is not read). A file or folder that is designed and not built yet is written with ` (planned)` right after its backticks; the mark comes off in the commit that creates it, and the gate fails it from then on (L-013).
- Tuning numbers change in `docs/GDD.md` and `src/config/tuning.ts` in the same commit. So do texts the GDD quotes (the language table, tip texts) and the code that holds them: tests that read `docs/GDD.md` compare them (L-051).
- A number or claim that follows from the simulation, a level's data or a layout (a height reached, a reach, where things land, from which inset a button meets a menu row) is measured by running the real code (over the real level) in a test, never worked out by hand (L-003, L-014). Before that code exists, write it as a target. A figure from the `implementer`'s report goes in only if the report marks it "exact", asserted by a test at that very value; one marked "not pinned" gets its test first. A figure measured by a scratch test outside the repository (a design agent's probe, a one-off script) counts as a target until a test in the repository pins it: the GDD says who measured it and how, and the figure is checked against the measured tables already in the GDD before it goes in (L-003). A sentence about a drawing (what lies behind the HUD, behind a body's rows, what shows through an opening) is measured on the drawing the same way, against the tuning number it leans on (L-072).

## Steps

1. Make the edit with exact-text edits, not a script that slices the file (L-002). Then **hunt stale sentences (L-013)**:
   - Re-read every section you edited in full, and its row in `docs/BACKLOG.md`.
   - Run `node scripts/check.mjs --gdd-hunt <GDD-ID,...> <term,...>` and read every sentence it lists. For each section the branch changed, and each GDD ID you give it, it lists the sentences elsewhere that name it and the status-word sentences on their line ("yet", "so far", "only", "not built", "built for", "checked by"), in the GDD, `docs/BACKLOG.md`, `CLAUDE.md`, `docs/HARNESS.md` and `.claude/` (a skill or subagent that quotes the old rule goes stale with it, also where it cites no ID: give such a rule's words as a term, L-053), and inside that section the sentences with a status word. Give it the IDs of what the change builds or alters without editing their section (a later phase of a feature edits none). Give it as terms, matched as whole words, what the change touches that has no ID: its names; its siblings' plain list text (the other menus, levels, enemies or sounds, such as "1-2 and 1-3": a sentence that lists them now misses the new one); the opposite of what the change now says ("not registered", "to come"); an old number it replaces; the path of a test file or block it deletes or moves. For a change that moves or flips things, give the positions it changes with `in:` before each (`in:left,in:right,in:above,in:top,in:bottom`), which searches the changed sections only.
   - For every number the edit writes, search for the rule that limits that quantity elsewhere (its name, as "raised bottom" or "rows under"), and keep within it or change that rule too (L-013, recurrence 28).
   - Fix every sentence the change makes false, in any section, then run the hunt again: a fix can leave a stale sentence of its own (L-013, recurrences 20 to 27).
   - **Work timing claims through (L-094):** a sentence that tells the player when to act (a cue, a rule of thumb, "before", "as", "while") is turned into steps from the section's own numbers (the step the cue happens, plus the action's steps) and checked against the window it claims, before it goes in; write the worked counts beside it, and check every other timing sentence in the section the same way, in every phase or case it names, not only the sentences you edited: read the section top to bottom for them, never only a search for the words of a known one.
   - **Check a measured figure's cause against the run (L-093):** a sentence that says why a measured number is what it is ("the gantry caps the jump", "the bat's loop") is checked against what the bodies were doing on the steps that made the number, every sample it covers, before it goes in; a decision the user makes on that sentence is asked again if the cause turns out wrong.
2. Bump `Version:` at the top, once per PR: a later GDD edit before the PR merges (a review fix, or a second commit made before the PR exists) amends that version and its changelog line instead of bumping again, raising it to minor if the PR now adds or deprecates an ID, and to the next free number if `origin/main` took that version meanwhile. The gate fails a branch that adds two versions (`gdd-one-version`, L-057). Minor if an ID is added or deprecated, major for a change to the design pillars (GDD-VIS-03), patch for everything else, new rules inside existing sections included. The IDs added or removed: `diff <(git show "$(git merge-base origin/main HEAD)":docs/GDD.md | grep -oE '^#+ GDD-[A-Z]+-[0-9]+') <(grep -oE '^#+ GDD-[A-Z]+-[0-9]+' docs/GDD.md)`. A minor version also runs the GDD-TEC-07 dependency review (its cadence is Proposed; `docs/HARNESS.md`, Dependencies): `npm outdated`, upgrade, the gate and the playtests, with the result in its changelog line or an ADR.
3. Add the changelog line at the top of the list: `- **x.y.z** (YYYY-MM-DD) GDD-AAA-NN, GDD-BBB-NN: summary`, naming every section the diff changes and no other (a minor version's dependency review may also name GDD-TEC-07; the gate's `gdd-changelog-sections` compares the IDs before the line's first colon with the sections that differ from the merge base; a section where only an Open Question's number changed may be named or left out), with the user's decisions quoted and dated. Write that a check passed (the gate, the playtests) only for a run that has finished on the code the line describes, and say where it ran; a later change to that code (an upgrade, a fix) makes the claim pending again until a new run finishes (L-084).
4. Update Open Questions: add new unknowns, mark a partial answer with `(user, YYYY-MM-DD)`, remove a fully answered one. Search the Open Questions for every thing the edit marks Decided (a name, a number, a rule): a question that still lists it as open is stale (L-013). Removing one renumbers the ones after it: fix every `Open Question N` in `docs/GDD.md` and `docs/BACKLOG.md` to match.
5. Sync the backlog: `node scripts/check.mjs --backlog-stub` prints rows for new IDs; paste them into `docs/BACKLOG.md`. Mark deprecated IDs `cut`.
6. Run `node scripts/check.mjs`. It must pass. Then read `git diff HEAD -- docs/GDD.md`: only the lines you meant to change moved. When the edit changes a rule, a status or a number (more than the wording of one sentence), launch the `pr-reviewer` subagent with the words `local GDD audit` in place of a PR number, and no `model`, before the commit, giving it the user's words for each decision the edit records and the IDs and terms you hunted, and fix what it finds: it reads the diff without this session's memory of it, which is how most stale sentences were found (L-013).
7. Commit a design-only change as `docs(GDD-XXX-NN, ...): <summary>`, after the `harness-retro` skill when this GDD edit is the whole task. A GDD edit that goes with code (a tuning number, a quoted text, a feature, a fix) goes in that code's commit, with its type (`feat`, `fix`).
